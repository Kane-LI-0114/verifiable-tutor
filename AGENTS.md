## Test-driven development

Every new feature follows the red, green loop. A feature is new or changed behavior in `src/verifiable_tutor/` or in a TACC job directory (`tacc/`); documentation and proposal edits are not features. A feature change without a test that failed first is not complete, even when tests cover it afterwards.

- Red first: write one failing test, run it, and confirm it fails for the intended reason. A test that fails to import, or fails on an unrelated assertion, is not red yet.
- Green second: write only enough implementation to make that test pass. Do not add behavior the current test does not require.
- One slice at a time: one seam, one test, one minimal change, then plan the next test from what the last cycle taught. Do not write a batch of tests for imagined behavior.
- Refactor after green, under the protection of the passing tests, and keep refactoring out of the red to green cycle.

Tests observe behavior at seams. A seam is the public boundary through which the feature can be observed, such as an exported module function, a deadline-registry query, a retrieval call, or an HTTP endpoint. Tests stay blind to internal structure: a test that breaks when internals are renamed but behavior is unchanged sits at the wrong seam.

- Before the first test of a feature, name the seams under test, each with one line on what it catches and what it misses. When the request does not name them, confirm the seams with the user before writing tests; no test is written at an unconfirmed seam.
- Aim tests at the critical paths and complex logic those seams expose, not at every edge case.
- Take expected values from an independent source: a worked example from the course material, a known-good literal, or behavior the proposal states. Do not recompute the expected value the way the implementation does, and do not assert a constant against itself.
- Mock only at process or network boundaries: the TACC model service, external LLM and search APIs, and the clock. Do not mock internal collaborators, and do not verify through a side channel (index files, caches, logs) what the interface already returns.
- Reproduce a reported defect with a failing test before fixing it.
- Name tests after the capability in domain terms, for example `test_before_deadline_refuses_complete_solution_and_offers_hint`. If the repository gains a `GLOSSARY.md` or ADRs near the change, read them and use their terms.

Tests live under `tests/` and mirror the package path: `src/verifiable_tutor/policy/gate.py` is tested at `tests/policy/test_gate.py`. The UI tests live inside the Vite project at `src/verifiable_tutor/ui/web/tests/` and are named after the route or page capability, because Vitest resolves the `@/` alias from the Vite project root. The frameworks and commands are recorded in [Toolchain and commands](#toolchain-and-commands).

## Conventions

- Write English documentation in GitHub-flavored Markdown with sentence-case headings.
- Do not use em dashes, en dashes, or a double hyphen as an aside. Use commas, colons, parentheses, or a single hyphen instead.
- One fact, one home. This file owns agent rules; [README.md](README.md) owns the project description and directory roles. Link instead of duplicating, and update the owning file when a fact changes.
- Prompt texts sent to a model live as one `.md` file per prompt under `src/verifiable_tutor/prompts/`, and application code loads them with `verifiable_tutor.prompts.load_prompt` instead of inlining prompt text in Python. The knowledge-base template `kb_v1.md` (system, `%%USER%%`, and `%%REPAIR%%` sections) is parsed by the TACC worker after `scripts/tacc/run_kb_job.py` stages a copy into the task directory. Model request parameters, including the TTS instruction default, stay in `config/models.yaml`.
- Keep the `.gitkeep` files for scaffold directories; they are why those empty directories exist in Git. Build-output directories are the exception: `src/verifiable_tutor/ui/static/` is generated by `npm run build`, ignored by Git, and has no `.gitkeep`.
- Never commit generated or runtime output: data, caches, logs, Slurm logs, temporary and scratch work, example outputs, environment files, or macOS metadata. `.gitignore` is the authoritative list of ignored paths; do not force-add an ignored file. The maintained API documentation bundle under `docs/api/` is the recorded exception: it is generated deterministically by `scripts/build_api_docs.py`, guarded by `--check` in pytest, and committed as the deliverable ([ADR-0013](docs/adr/0013-local-offline-swagger-ui.md)).
- `.env.example` is the only environment file that may be committed, and it must contain no real secrets.
- Do not edit the proposal `.docx` or `.pdf` binaries by hand. Rebuild the DOCX from the script; the v1 PDF is manual and frozen, and the v2 and v3 PDFs are exported with the recorded `soffice` command.
- Never commit course PDFs or transcripts: the contents of `data/corpus/` are gitignored so course materials are not redistributed.
- `benchmarks/results/` is not gitignored (see Known gaps). Stage only small, curated result files there.

## Commits

Commit every stage of work as soon as it is complete, without waiting for the user to ask for a commit. A stage is one logical change that stands on its own: a feature slice that just passed its test, a documentation edit, a regenerated artifact with the source that produces it, or a fix with its regression test. Commit the stage, then start the next one.

- Make every commit with the `git-commit` skill of the agent harness, invoked as `/git-commit`. The skill reads the diff, stages the related files, writes the Conventional Commits message, and runs `git commit`; do not hand-write a message the skill would produce differently.
- Commit messages follow Conventional Commits with a scope, matching the existing history: `chore(repo): initialize project repository` and `docs(proposal): add student IDs to title block`. Keep one logical change per commit.
- Stage the files of the stage by path, and only those files. Do not use `git add -A` or `git add .`: the working tree can hold another agent's unfinished work, and a stage that mixes two changes has to be split instead of committed whole.
- Do not commit a red test without its implementation, a stage whose tests fail, or a generated artifact that its own build or `--check` has not refreshed. The conditions in [Before claiming a change is done](#before-claiming-a-change-is-done) hold for the stage before it is committed.
- Change nothing in the Git configuration, and do not create an empty commit when the stage changed nothing.
- Do not push, amend, rebase, or otherwise rewrite history unless the user asks. The `git-commit` skill stops at the local commit.
- If the stage was made by a delegated agent, the agent that made the change commits it, so the work does not come back to the parent as an uncommitted working tree.

## TACC and model serving

This repository is a standalone Git repository nested inside the course workspace at `../../`, so paths beginning with `../../` are outside the repository and do not resolve on a hosted copy. The project targets the course TACC@HKUST platform. `tacc/env-spike/`, `tacc/ocr-smoke/`, `tacc/pdf-parse/`, `tacc/ocr/`, `tacc/index/` and `tacc/serve/` are committed jobs; `tacc/exec/` and `tacc/client/` are planned task directories. Every job copies its task tree to a private jobhome at start, because a later submit from the same account re-syncs the shared `TACC_WORKDIR` with `rsync --delete`. The authoritative workflow is the course documentation outside this repository: the course workspace instructions in `../../CLAUDE.md` and the copies in `../../tacc-env-docs/`. Treat this section as a pointer, not the authority. All paths in this section are on TACC or inside a task directory, not in this repository.

- TACC is a required model-serving backend: the BGE-M3 index job and the Qwen knowledge-base job are submitted jobs that write their output to `USERDIR`, and the backend polls, downloads, validates, and caches the results. No SSH forwarding or inbound service is used ([ADR-0011](docs/adr/0011-tacc-as-required-model-serving-backend.md)).
- The course uses the official SDK CLI: configure with `tcloud config -u USERNAME -f PRIVATE_KEY`, then `tcloud init`, and submit from a task directory containing `tuxiv.conf` with `tcloud submit`.
- Inspect a job with `tcloud ps -j JOB_ID`, read its log with `tcloud cat slurm_log/<task>-<JOB_ID>.log`, fetch outputs with `tcloud download <remote> <local>`, and release resources with `tcloud cancel -j JOB_ID`.
- The Qwen knowledge-base job is required and lives in `tacc/serve/`: vLLM loads `qwen3.8-27b` at tensor parallel 2 and 32K context inside the job, reads the request and input chunks from `USERDIR`, writes knowledge records and progress, and exits. Interactive text generation uses external OpenAI-compatible APIs ([ADR-0005](docs/adr/0005-external-model-apis-as-primary.md)), configured in `config/models.yaml` with keys in `.env`; Qwen is not a chat provider ([ADR-0011](docs/adr/0011-tacc-as-required-model-serving-backend.md)). The backend and UI are not a TACC job; `tacc/client/` is the offline evaluation job.
- `SERVICE_BASE_URL` and the client `server-url.txt` flow are not used: SSH port forwarding is not supported, so the Qwen job runs inside the submitted job and exchanges files through `USERDIR` ([ADR-0011](docs/adr/0011-tacc-as-required-model-serving-backend.md), [docs/tacc-notes.md](docs/tacc-notes.md#staff-clarification-2026-11-01)).
- Hard constraints: cancel GPU jobs when finished; `/mnt/home/public/course-envs/CSIT6000V/` is read-only, so never install dependencies into it or modify it; on the `tacc` partition, Slurm exports host-global CUDA device indices while the container enumerates devices from zero, so CUDA jobs must `unset CUDA_VISIBLE_DEVICES` or CUDA reports no CUDA-capable device.
- No custom images: the SDK job schema has no image field, and accounts have no Docker or root. The dependency strategy is a hash-pinned project environment installed into `$HOME` ([ADR-0001](docs/adr/0001-pinned-python-environment-without-docker.md)); GPU work keeps the public environment.
- Keep one entrypoint item per job: the SDK joins multiple entrypoint entries into a single command line. Keep task directories to code, because a submit directory is capped at 1 GiB; put corpus, page images, indexes, and weights in `USERDIR` or `$HOME` with `tcloud upload`.
- Platform mechanics measured from the SDK source and the live cluster configuration (submit cap, persistence, single entrypoint, container facts) are recorded in [docs/tacc-notes.md](docs/tacc-notes.md#platform-mechanics-2026-10-28).
- Compute nodes are private and have no inbound path from a laptop. The 2026-11-01 clarification states that SSH port forwarding is not supported, so the delivered system does not use it; all TACC access is job submission and `USERDIR` exchange ([docs/tacc-notes.md](docs/tacc-notes.md#access-from-outside-2026-10-28), [ADR-0011](docs/adr/0011-tacc-as-required-model-serving-backend.md)).
- The scheduler enforces a one-hour limit: `sinfo` reports `TIMELIMIT 1:00:00` for the `tacc` partition, so every job requests `time=00:59:00`. Every TACC job is a batch job that must fit that window; the Qwen knowledge-base job measured a 434 s vLLM cold start on 2026-11-02 (job 28067) and should be sharded by document and pre-built for the demo. Staff clarifications from 2026-10-28, 2026-10-30, and 2026-11-01, with the job and storage budgets, are recorded in [docs/tacc-notes.md](docs/tacc-notes.md); that file owns them.
- `tacc/pdf-parse/` is the demo prototype: one PDF in, per-page records plus one document markdown out. `scripts/tacc/parse_pdf.py` is the local request interface that submits it.

## Before claiming a change is done

- Docs: every cited path and relative link resolves from this directory (`test -e` each one), no em dash or en dash appears, no double hyphen is used as an aside, and every claim traces to a file in this repository or to the course docs described above. After an API change, run `.venv/bin/python scripts/build_api_docs.py` and commit the regenerated bundle with the change.
- Proposal changes: rerun the matching build command (`python3 proposal/build_proposal.py` for v1, `--version 2` for v2, `--version 3` for the current proposal), inspect `git diff` for the generated Markdown and DOCX, re-export the PDF and previews if the DOCX changed, and confirm the document is still two pages. Leave v1 and v2 assets untouched unless they are being revised deliberately.
- File hygiene: `git status --short` shows only the intended files, scaffold `.gitkeep` files are untouched (the generated `ui/static/` directory is not tracked), and no generated artifact, cache, log, environment file, or benchmark dump is staged.
- Commits: the stage is committed with the `git-commit` skill. A stage that is complete but uncommitted is not finished; the workflow is owned by [Commits](#commits).
- Features: every slice has a test that was seen to fail for the intended reason before the implementation, passes after it, and the seams covered are stated in the change description.
- Code: run `.venv/bin/python -m pytest` locally and the same suite on TACC when a job can execute it, cancel any GPU job started for the test, and record the exact command used.
