# ADR-0014: Persist conversation turn metadata and generate the physical data model

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-11-04 |
| **Deciders** | LI Jinchuan (project lead); recorded by the engineering agent |

## Context

The chat UI renders a work chain (work steps, model thinking, citations, tool calls) beside each answer. Before this decision the backend persisted only the answer text: the streamed `data-step` and `reasoning-*` frames existed in the JSONL session trace and in the live stream, but not in SQLite. Every history load therefore rebuilt the conversation from text-only rows, so a refreshed or reopened conversation lost its work chain and thinking. The first answer of a new conversation made it visible: completing it navigated to `/chat/:id`, which remounted the page, loaded the stored history, and dropped the streamed metadata. A route-level workaround (handing the streamed messages to the opened conversation) moved the symptom instead of fixing it.

The PRD requires a user-visible work chain per answer (FR-B9), tool calls with command line, exit code, and output (FR-H3), per-user conversation history with resume (FR-B11), and a session trace that can be replayed without model calls (FR-B10). The JSONL trace is the canonical record for replay and evaluation, but it is a file and is not the store the history endpoint reads. The PRD logical ER (Figure 6) is a target domain model; it does not describe the tables the code actually creates, and there was no maintained description of the physical schema or its migration version.

## Decision

**Normalized turn metadata in SQLite.** Schema version 1 adds three columns to `messages` (`reasoning`, `model`, `thinking`) and three child tables, each cascading from `messages`:

- `message_steps`: ordered work-chain steps with step name, status, detail, duration, policy state, and rule id.
- `citations`: quoted page spans per answer with document id, page number, normalized highlight box, and verifier time.
- `tool_calls`: typed tool calls with name, command argument vector, exit code, truncated output, and status.

List-shaped metadata is normalized instead of stored as one JSON column because citations and tool calls are first-class review and verification evidence, and because the PRD already models a citation as a table. A turn's metadata is written in one transaction with its assistant message, so an answer either has all of its metadata or none of it.

**Write path.** `ChatService` accumulates `data-step` frames (first-seen order, last state wins) and reasoning deltas while it streams, then persists the whole turn through `Storage.add_assistant_turn` before it emits the `finish` frame. A client that sees the answer complete can therefore read it back from the history immediately. The stored assistant message id is the streamed `start` message id, so the live stream, the stored message, and the trace share one id. If persistence fails, the transaction rolls back, the trace records an error event, and the stream ends with an error frame instead of `finish`, so a turn is never reported as finished when it is not stored. Aborted and mid-stream-failed turns still store nothing.

**Read path.** `GET /api/sessions/{id}/messages` returns the metadata with each message; the UI overlays it onto the AI SDK message state by message id and reuses the existing work-chain, reasoning, citation, and tool-call components. The previous streamed-state handoff is deleted: every conversation, including the one a first answer opens, renders from the persisted history.

**Record ownership.** The JSONL session trace remains the canonical record for replay and evaluation; SQLite is the user-facing projection for history. The two are written from the same frame stream, and a disagreement would be a defect. The trace keeps sub-frame timing and re-emits through the replay endpoint; the database keeps the domain metadata a history view needs.

**Legacy data.** `Storage.initialize` upgrades an existing database in place: it runs the current schema, adds missing `messages` columns, creates the new tables, and sets `PRAGMA user_version = 1`. Existing answers were filled once from their recorded traces with a one-off local script that is deliberately not retained: it matched a trace turn to an assistant message by exact answer text (legacy trace message ids differ from stored ids), filled only empty fields, and inserted steps only when the answer had none. The retained upgrade path is the schema migration; existing answers that predate the traces' metadata keep empty fields.

**Physical data model documentation.** `docs/physical-data-model.md` and `docs/figures/physical-db.dot` are generated by `scripts/build_data_model.py` from a temporary database created by the real storage schema, so they list the actual tables, columns, types, keys, indexes, checks, and schema version. `--check` and a pytest drift guard fail when the committed page is stale, and a missing table or column note fails the same guard. The page states its difference from the logical PRD model and links both ways: PRD Figure 6 is the intended domain model, the generated page is what runs.

## Consequences

**Positive:**

- A reloaded conversation keeps its work chain, thinking, citations, tool calls, and model profile; the defect is fixed at the history seam instead of in a navigation workaround.
- The video-demo path and the offline replay path now show the same answer content, one from SQLite and one from the trace.
- The schema is versioned and upgrades in place, so existing local data survives the change.
- The physical schema is documented without hand-maintenance drift, and the logical and physical models are explicitly separated.
- Citation and tool-call tables land once, so the evidence and tool layers do not need a second schema migration to expose their data.

**Negative:**

- Turn metadata is stored twice: once in the JSONL trace and once in SQLite. The trace stays canonical for replay and evaluation, so the copies must be written from one source and are covered by tests.
- The history response is larger because reasoning text and steps travel with every answer; this is acceptable at course-demo scale and there is no pagination yet.
- Removing the streamed-state handoff means the conversation a first answer opens performs a normal history load, which briefly shows the history loading state. Persisting before the `finish` frame makes that load reliable.
- The generated physical page must be regenerated whenever the storage schema changes; the drift test enforces it.

**Neutral:**

- The API version and project version do not change; the history response only gains fields.
- `provider` and `tier` keep their request-time meaning on stored rows; `model` and `thinking` record the resolved selection for later display and traceability.
- The physical page documents schema, not runtime data: `data/app/` stays ignored and row counts are not committed.

## Alternatives considered

**One `metadata_json` column on `messages`.** For: one write, one read, matches the UI message shape. Against: citations and tool calls are evidence that later queries and verification need, the PRD already models a citation as a table, and a JSON column would need a second migration to become queryable. Why not chosen: normalization is cheap at this scale and keeps the domain records first-class.

**Derive history metadata from the JSONL trace.** For: no schema change, trace already canonical. Against: the history endpoint would parse files and couple the HTTP response shape to wire frames, traces are per-conversation files rather than a queryable store, and a missing trace would silently degrade history. Why not chosen: keep the trace canonical for replay and evaluation, and give history a proper projection.

**A `turns` parent table above user and assistant messages.** For: a natural place for per-turn metadata. Against: the existing `messages` table already orders the conversation, the user and assistant rows are separate messages, and the change would move every existing row. Why not chosen: a `turns` table adds indirection without a query it enables.

**Keep the route-level streamed-state handoff and store nothing.** For: no schema or API change. Against: refresh, sidebar switch, and reopening still lose the work chain, which is the reported defect. Why not chosen: it treats the symptom, not the history seam.
